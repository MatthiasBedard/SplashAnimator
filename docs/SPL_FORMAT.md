# Splash Animator project format

The current reader accepts manifest versions through 61. Version 59 includes persistent symbol base-track preferences. Version 60 adds symbol timeline masks. Version 61 stores a scene catalog. The document and manifest have separate version checks in [storage.ts](../packages/document/src/storage.ts), and the embedded document is migrated and validated in [index.ts](../packages/document/src/index.ts).

The sections below record historical format changes. Statements about the current version in those sections apply to their original checkpoint.

## Schema 59: persistent symbol base-track preferences

Current documents and writers/manifests use 59. Earlier schema sections below are historical. Symbol definitions may store baseLayer {name,visible,locked,outline?,outlineColor?} for their reserved @base layer. Name is a nonblank string of at most 80 characters; visible/locked are booleans. Outline preferences use the existing layer validators. Only plain own enumerable data fields from this exact set are accepted; getters, inherited/nonenumerable/symbol keys reject before reads. Omission preserves Artwork/visible/unlocked defaults and does not serialize new preferences. Base identity and initial artwork/keys remain separately owned.

Visibility applies to symbol rendering/exports; lock and outlines affect authoring. Scene/definition editing, local history and library publication preserve registration, keys, paint, assets and unrelated metadata. Schemas 0-58 reject forward baseLayer fields before upgrading; old files without it migrate with unchanged data/IDs. A schema 59 document requires a 59 manifest. Schema58 saved root mask membership and all earlier contracts remain unchanged.

Optional `frameComments` tables belong to the scene document or a symbol's `timeline`. Each `{frame, text}` record uses a unique, zero-based frame within that timeline, ordered by frame. Nonblank multiline text is limited to 2,000 UTF-16 code units per comment and 262,144 per timeline. Layer exposure edits keep comments at their original frame numbers. Comments are editor metadata and do not enter exported playback data.

Additional symbol timeline layers can persist `drawingMode` as `object` or `merge`. Omitted modes retain the shared editor's artwork-based defaults. Explicit Merge layers follow the same group and symbol placement validation as scene layers.

## Schema 57: restricted original distance timing on independent group banks

Current writers/manifests use57. Older schema sections below describe historical contracts. An optional group binding field restrictedArc stores {descriptor:{version:1,cubic:[four original relative x/y points],from,to},origin:{x,y}}. The original cubic begins exactly at0/0; finite increasing absolute progress windows remain within0..1. The field is separate from actual MotionPath controls and must be omitted when unused. It requires a sparse root independent additive single-cubic distance route, no tangent/waypoints/shared path/orbit/grouped symbols, fixed bases and complete original membership with exact member travel.

Raw validation rejects getters, sparse/extra/inherited malformed data, unsupported versions and nonfinite/unresolved/overflow geometry before transport. Document/save and animation validation reconstruct actual relative controls/endpoints and bind them to the original restricted blossom using existing numeric tolerance and the unchanged original adaptive table. Root/layer/key/vector/symbol/ordinary-path placement rejects. No timing table is serialized or regenerated from half geometry. Metadata-free sampling remains exact; existing artwork/resource limits persist.

Schemas0-56 reject forward fields before migration; absent data upgrades without defaults. A schema57 document requires a57 manifest. Actual old56 directories remain readable and save as57. Reopen and unrelated checked channel updates preserve timing. Checked independent bank/control edits discard only the selected bank descriptor when controls meaningfully change, preserving distance mode; no-op edits reject. Stale generic controls/endpoints cannot be saved with old timing. Generic restricted subdivision/staging stays guarded pending full candidate proof. A separately named private preparer can return preserving split Projects only after continuous/original-table, full integer artwork and complete source/library/all-track admission for linear geometry/unchanged properties. It enables no UI/history action. Schema admission does not qualify arbitrary half easing, recursive persisted subdivision or complete M4.

## Schema 54: sparse root live-motion recipes

Optional root timeline-layer `liveMotionSpans` stores `{id,start,end,ease,opacityEase?,paintEase?,options?,path?,rotation?,correspondence?}`. It is a separate record array from baked `motionSpans`: no `baseline` or `autoRefresh` field is allowed. Existing easing/options/path/correspondence/rotation validators apply, with explicit paint admission and root-only unsupported group/symbol continuity guards. Ranges are sorted, distinct, at least two frames long, within duration, and may share exact endpoints. Two nonempty authored endpoint keys are required; interior keys, overlapping live/baked/opacity ownership and ambiguous identities reject. No generated vector keys are serialized.

The field is reserved to root layers and rejects on document/symbol/base/additional timelines. Current manifests/documents use54. Schema0-53 migration adds no live defaults, rejects forged new fields and retains artwork/IDs/assets/settings plus previous historical feature gates. Schema54 documents require matching current manifests. Geometry compatibility is qualified by the detached animation API; structurally valid incompatible endpoints can load for explicit recovery but cannot silently sample. The ordinary stage authoring/Test Movie/export remains on its existing path. Control > Preview live timeline explicitly renders sparse root poses in a detached read-only still; remembered child preparation is separately opt-in. This does not enable live tween creation or stage editing controls.

## Schema 47: root opacity bindings

The optional manifest document field `opacityBindings` is an array of `{layerId, shapeId, start, end, keys}`. The interval is inclusive, in absolute zero-based root frames. The target must exist uniquely in every intersecting held exposure, with the same artwork kind and symbol definition. Multiple bindings for one target must not overlap. Keys are strictly increasing `{frame, opacity, ease?}` entries inside the interval. Opacity is finite in [0,1]; an outgoing segment accepts the existing motion easing values or `hold`, defaulting to linear. The first/last value holds to the interval boundaries. Outside the interval the binding has no effect.

Projects through schema 46 migrate without adding bindings. A legacy root carrying the field rejects, even if the array is empty; it is not valid on layers or symbol definitions/timelines. Saving validates the original key values and lifetimes before writing a new revision. The detached HTML presentation runtime evaluates root channels at paint time. The editor stage and Test Movie also evaluate root channels for painting. Editing tools operate on the authored exposure. The object inspector can add a channel for one selected root object on an unlocked object layer. Its frame fields are one-based and opacity is entered as a percentage. At a frame inside a stored interval, Edit opacity channel loads that binding for revision or removal. The inspector offers preset easing and holds and preserves a saved custom curve when editing other values.

## Schema 41 - Main-frame TypeScript sources

Optional `document.frameScripts` stores sorted unique `{ frame, source }` pairs for absolute zero-based main-timeline frames. Positions must be safe integers within duration; at most 10,000 bodies and 256 KiB aggregate UTF-8 text are accepted. Empty source remains authored. Missing field means no scripts. Sources belong to the main timeline, not artwork keys, layers or symbol definitions: artwork moves do not retime them. Duration reductions that strand sources fail validation. Source text is stored in the manifest and preserved by explicit save, autosave/recovery and directory duplication; no compilation or execution occurs on load. Schema 0-40 files upgrade without sources. A reserved frameScripts field in an older version rejects, and older readers reject schema 41. This format does not yet enable preview/HTML scripting.

## Schema 40: saved node matching

Optional motion-span `correspondence.nodes` stores a boolean (straight matching enabled/disabled) or `{ hints?, curves?, distance? }`. Hints contain one array per contour, each containing strictly increasing positive integer `[source, target]` interior-anchor pairs. Endpoint bounds and contour counts validate during generation. `distance: true` requires `curves: true`; an object requires hints or curved matching. Arrays detach on capture and refresh uses saved values. Exact endpoint geometry and existing bounded subdivision remain unchanged. Schema 39 retains only its original alignment fields while upgrading; earlier ignored-field migration remains unchanged.

# .spl directory format - schema 39

Schema 39 adds optional recipe `correspondence: { start?: number | number[], reverse?: boolean | boolean[], order?: number[] }`. Starts are nonnegative safe integers, lists are nonempty, directions are boolean, and order is a complete zero-based permutation. Unknown keys reject. Endpoint-specific counts and open-path constraints remain generation checks. Missing fields keep existing defaults. Creation snapshots the controls; refresh/retiming reuse saved values. Older schema input discards this formerly ignored recipe field before normal migration to 39; older readers reject 39. Node-pair hints and resampling modes remain unsaved.

Schema 38 extends recipe `options.gradientStops` to `boolean | "ordered" | { pairs: "auto" | [number, number][] }`. Explicit pairs must cover ordered group indices monotonically from zero with no skips, reversals or duplicate pairs, with at most 32 pairs. Endpoint-specific coverage and the expanded-stop bound remain generation checks. Ordered and pair matching require paint and gradient geometry interpolation. Automatic matching is recomputed from current endpoints on refresh. Saved values detach; schemas 31-37 retain their original boolean-option rules. Supported older files migrate to 38; older readers reject 38. Node correspondence is not yet stored.

Schema 37 adds optional boolean recipe options `gradientStops` (fixed-offset gradient stop resampling) and `gradientPremultiplied` (opacity-weighted encoded RGB interpolation). Missing values mean false. Both require paint interpolation when generating; saved values are reused by refresh and retiming. The existing 32-stop expansion bound and authored endpoint preservation remain unchanged. Schemas 31-35 accept only their original seven option keys; schema 36 accepts its twelve keys and rejects these new flags. Supported older files migrate to 37; older readers reject 37. Ordered gradient mappings and node correspondence are not saved by these options.

Schema 36 adds optional boolean recipe options `contourAreas`, `contourEdges`, `contourContacts`, `curveTangents` and `curveSelfContacts`. Missing values mean false. Generation requires matching nodes for these existing bounded guards; refresh and retiming reuse saved flags. Contacts takes precedence over edges, which takes precedence over area-only checking. Schema 31-35 input still rejects these previously unknown option keys; earlier ignored-option migration behavior is unchanged. Supported older projects migrate to 36; older readers reject 36.

Schema 35 adds optional boolean recipe `autoRefresh`. Absent/false means manual; true enables guarded authoring-time regeneration after retained endpoint edits, including after reopen. Session override may refresh all recipes. Policy edits preserve artwork and do not themselves regenerate existing conflicts. Schema 34 and earlier migrations remove formerly ignored flags, preserving previously supported metadata. Older readers reject 35; playback still consumes baked keys.

Schema 34 permits recipe `ease` to be a preset string or `{ kind: "cubic", x1, y1, x2, y2 }`, with all controls finite in 0..1. The time coordinate is inverted before progress is sampled. Creation stores detached curve controls; explicit/automatic refresh and retiming use saved values. Schema 33 migration retains existing records; schemas 29-33 continue to reject non-preset easing on input. Earlier ignored-field rules remain unchanged. Older readers reject 34.

Schema 33 adds optional remembered recipe `rotation`, sharing the existing motion rotation validator: direction/extra turns, rigid group mode/depth, uniform or independent-axis scale, X shear and custom/saved leader pivots. Capture is optional; refresh and retiming use the detached saved settings. Endpoint group compatibility, affine/property requirements and pivot/path conflicts remain generator checks. Schema 32 migration preserves paths/options/recipes/pivots and removes formerly ignored rotation metadata; earlier rules remain intact. Older readers reject 33.

Schema 32 adds optional remembered recipe `path`: finite start/end control offsets, optional straight or curved waypoints, linked or independent incoming/outgoing handle offsets, distance timing and tangent flags. It uses the shared motion-path validator; geometric/stationary/work-budget checks occur when generating or refreshing. Paths are detached snapshots, with offsets interpreted relative to current endpoints. Refresh and retiming use saved paths. Schema 31 preserves recipes/options/pivots but strips formerly ignored paths; older migration rules remain intact. Older readers reject 32.

Schema 31 adds optional recipe `options` with boolean `affine`, `paint`, `nodes`, `primitives`, `strokeWidth`, `gradientGeometry` and `gradientBasis` fields; unknown keys/nonboolean values reject. Missing fields mean false. Creation controls are separate from advanced motion settings; refresh and retiming use stored options. Schema 29/30 migrations preserve supported recipes and remove formerly ignored options; older migrations retain their historical rules. All supported old versions now migrate to 31. Paths, group controls, matching hints, custom easing and topology guards remain outside the stored recipe format. Older readers reject schema 31.

Schema 30 adds optional `symbol.timeline.motionSpans` for the base artwork track, using the same recipe format as layer records below. Additional symbol tracks retain their layer records. Schema 29 migrations preserve existing layer recipes and pivots while removing formerly ignored base-track recipes; schemas 0-28 retain their historical migration rules. All supported old schemas migrate to 30; older readers reject schema 30. Main and symbol editors provide explicit create/refresh/detach and span-retiming controls with isolated history. Span retiming preserves its ID/start/easing, moves the exact target artwork and regenerates its baseline/end, retaining outside timing and duration by default; collisions or shared targets reject. Optional ripple retiming shifts following keys and recipe ranges/baselines together after checking unchanged interiors, preserving their IDs/easing/artwork. Total duration and button mappings remain fixed; overflow rejects. Symbol transactions enforce the existing aggregate artwork budget before generating keys. Both editors offer opt-in session automatic endpoint refresh; its preference is not serialized. Conflicts preserve endpoint edits and existing interiors. Broader path/group/correspondence recipes and per-span persisted live settings remain unsupported.

Schema 29 adds optional layer `motionSpans` records for remembered basic motion recipes. Each record has a unique layer-local `id`, integer `start`/`end` (at least two frames apart, within 0-99999), built-in `ease` (`linear`, `in`, `out`, `in-out`) and a `baseline` string containing the exact JSON serialization of generated interior keys. Records are sorted and may share endpoints but cannot overlap interiors. The baseline is comparison data only, never parsed or rendered. It intentionally remains loadable after unrelated timeline changes: explicit refresh rejects any changed/missing interior keys or invalid current endpoints. These records do not change rendering or automatically update keys. Detach removes the recipe while preserving artwork. The basic recipe controls are available in main and symbol timelines.

Schemas 0-28 migrate to 29 with formerly ignored `motionSpans` fields removed. Schema-28 project/symbol pivots remain intact; older pivot migration rules below still apply. Older readers reject schema 29. Recipe metadata roundtrips in saves/autosaves; main layer metadata is stored in the timeline file alongside key references.

Schema 28 adds optional `multiFramePivot: { x, y }` to the project and each symbol definition. Coordinates use the project or symbol's own drawing space, must be finite and within the existing document coordinate range, and may lie outside artwork bounds. These are explicitly remembered editor pivots; current selection and transient pivot gestures are not serialized. Metadata is included in normal saves, autosaves and recovery without rewriting artwork. Schemas 0-27 migrate with formerly ignored pivot fields removed; readers supporting only schema 27 or earlier reject schema 28.

Schema 27 adds optional symbol `buttonStates: { up, over, down, hit }`, with validated zero-based mapped frames. Playback clocks and interaction state remain session-only.

Schema 26 permits independent `movie` playback on symbol instances within symbol definitions, including later keys and additional tracks. Playback clocks and compiled topology are session-local; only existing instance playback settings are persisted. The complete dependency graph still rejects cycles, missing references and excessive depth/expansion, including hidden and unused artwork. Schemas 0–25 migrate without changing IDs or artwork. Readers supporting only schema 25 or earlier reject schema 26 rather than silently rendering nested movies as graphics.

Schema 25 adds independent symbol timeline layers; the definition's base artwork remains the bottom track. Schema 24 adds nested graphic symbol references with bounded recursive evaluation. The earlier format notes below describe the features introduced by each historical revision.

Schema 23 extends `symbolPlayback.mode` with `movie`. First-frame bounds are unchanged; elapsed playback clocks are session-local and are never saved. Schemas 0–22 migrate without altering graphic behavior. Older readers reject schema 23. Movie instances remain ordinary references to one-track symbol definitions; nested references and scripts remain unsupported.

Schema 22 adds optional instance `symbolPlayback: { mode: "loop" | "once" | "single", firstFrame }`. The frame is a zero-based integer 0–9999. Playback resolution clamps it to the definition's last frame; absent settings mean loop from zero. Only symbol instances may carry these settings. Schemas 0–21 migrate with prior playback unchanged; old readers reject schema 22.

Schema 21 adds optional symbol `timeline: { duration, keys }`. Duration is an integer 1–10,000; keys are strictly ordered, noninitial frames within duration. Frame zero uses the existing definition `shapes`; later keys can be blank. Every key uses the normal shape/group/paint validator and forbids nested symbol references in this subset. The 100,000-symbol-artwork budget counts all keys, and asset references across all keys remain protected. Schemas 0–20 migrate without changing artwork; older readers reject schema 21. These are document-FPS graphic loops, not independent movie-clip clocks.

Schema 20 adds optional `symbols` definitions (unique IDs, names, bounds and static vector artwork) and `kind: "symbol"` instances with a validated `symbolId`. Definitions cannot contain symbol instances in this first version. Instances belong to object layers. The library is limited to 128 definitions and 100,000 total definition shapes; expanded rendering is bounded separately. Bitmap references in definitions participate in asset validation/protection. Definitions persist in manifest document metadata, while timeline instance references use existing immutable vector revisions. Schemas 0–19 migrate to 20; older readers reject it. No movie-clip timeline data is represented yet.

A project is an actual directory ending in `.spl`, not a ZIP/file extension disguise. All references are portable relative paths; assets remain inside the project. Paths with traversal, absolute roots, backslashes, empty segments, colons, or symbolic links are rejected.

```text
Example.spl/
  project.json                         # atomic commit point
  scenes/main-<revision>.json           # scene → timeline
  timelines/main-<revision>.json        # layers and frame → vector-set refs
  vectors/<revision>.json              # editable object sets
  symbols/                             # reserved; definitions currently live in manifest metadata
  scripts/main.ts                      # preserved; not executed
  assets/{images,audio,video,fonts,imported}/
  settings/export.json
  .splash/autosaves/latest.json         # recoverable dirty snapshot
  .splash/autosaves/previous-<id>.json   # earlier committed manifest
  .splash/cache/
```

Unlike the illustrative prompt paths, scene/timeline/vector filenames include revision UUIDs. This ensures a partially written save never mutates the files referenced by the previous manifest. The manifest is small JSON with `format: "splash-directory"`, `schemaVersion: 26`, `revision`, ISO `savedAt`, document metadata and three relative references. Frames are zero-based internally, one-based in the UI. UUIDs identify documents, layers and shapes; shape IDs persist across a copied keyframe to allow later animation correspondence. They must be unique within each keyframe. A duplicate selection receives new IDs.

Layer arrays are bottom-to-top. Keys are sorted, unique, start at frame zero, and are less than duration. An empty vector set means a blank keyframe. Other frames hold the last preceding key's objects. Vectors have kind, X/Y, dimensions, rotation in degrees about the top-left, six-digit fill/stroke colors, stroke width and local polyline points. Samples may carry pressure from 0–1, tiltX/tiltY and twist. Schema 2 adds cubic nodes with optional incoming/outgoing handles, closed paths, brush settings, rounded corners, compound polygon contours/fill rules, gradients, paint opacity/caps/joins, drawing mode and static text (including axis scales). Layer drawing mode is object or merge. All new fields have backward-compatible defaults. This is still a subset of the intended authoring model. Merge rebuilding replaces affected region/stroke IDs; ordinary object edits preserve IDs.

## Transaction protocol

1. Validate and snapshot the full document; assign a fresh revision.
2. Exclusively create and flush the scene, timeline and vector revision files.
3. Exclusively acquire a per-manifest lock file. Compare existing manifest bytes with the caller's expected bytes. A mismatch is a conflict, never an overwrite.
4. Preserve the previous manifest in `.splash/autosaves`, write and flush a unique temporary manifest, then rename it onto the commit target.
5. Release the lock. A crash before step 4 leaves the old project loadable; orphan revisions can be inspected but are not auto-promoted.

Atomicity is at the manifest replacement, not at the whole directory. Parent directories are not explicitly fsynced, so power-loss durability depends on OS/filesystem guarantees. Network shares and hostile concurrent local filesystem changes are not qualified. A process crash while holding a lock may leave a stale `.lock`; no automatic lock stealing is implemented. Close all writers and inspect backups before removing one. Revisions/backups currently accumulate; do not delete revision files still referenced by a current or recovery manifest.

Every 15 seconds, a dirty saved project writes a separate recovery revision; explicit Save does not overwrite original assets. The browser/webview also caches unsaved project data in localStorage, bounded by available quota. Startup offers recovery rather than silently replacing the active document. LocalStorage is a convenience, not a substitute for a saved folder. Native recovery reauthorizes the original directory through a picker. Missing referenced assets are reported when opening; their bytes are never fabricated.

New/Save As create destinations exclusively. Save As copies all existing files, including unknown future data and imported originals, then commits the current document. A failed duplicate may leave a partial destination for inspection; it never deletes the source or silently retries into that destination. Current IDs remain stable when copying a project; this is a filesystem duplicate, not a collaboration fork.

Current migrations accept the internal flat schema-0 prototype and schema-1/schema-2/schema-3/schema-4/schema-5/schema-6/schema-7/schema-8 flat/directory projects, retaining IDs, geometry and asset references. Saving writes schema 9; migration does not rewrite asset bytes. Physical migration roundtrips are tested. There is no released schema-0 directory format. Future versions fail closed and must add explicit migration tests. JSON files are limited to 32 MiB by adapters. Validation bounds stage size, fps, duration, layer count, path points and geometry. The renderer still needs stress testing for adversarial complexity within those limits.

Recommended project Git ignores: `.splash/cache/`, `.splash/autosaves/`, `*.lock`, `*.tmp`. Track the manifest and referenced revision files. Garbage collection/compaction needs a later transactional design. Keep generated HTML/video/app exports outside `.spl`.

Optional `groups` on each vector stores up to 32 outer-to-inner group IDs. Members occupy contiguous stacking spans with consistent ancestry within a keyframe. Group coordinates are layer coordinates; no extra renderer transform is needed. Copy/duplicate remaps groups together; held/copied keyframes preserve identity. Older schema-2 builds do not implement group interaction and should not be used to edit grouped projects.

Optional project `guides` stores at most 1,000 unique IDs, x/y axes and finite bounded document positions. Guides are authoring-only and excluded from rendered preview/export.

Optional vector `transform: [a,b,c,d]` is a local affine basis after the existing rotation, with x/y as stage translation. Optional `pivot: {x,y}` is local to that vector. Original geometry and brush samples are preserved. Matrix validation rejects non-finite, excessive or singular bases. Schema 3 introduces these affine fields. Older clients reject the version instead of silently rendering transformed artwork incorrectly.

Schema 4 adds optional text `lineHeight` (0.5–5 times font size, default 1.2) and `letterSpacing` (-20–200 local pixels, default 0). Older schema-3 readers reject schema 4 instead of silently ignoring layout fields. Existing fonts, geometry, IDs and assets are retained during migration.

Schema 5 adds optional text `wrapWidth` (0–100000 local pixels; zero/missing keeps explicit newlines only). Source content remains unchanged. Older readers reject schema 5 rather than ignoring automatic line breaks. Schema-4 directories upgrade without rewriting asset bytes.

Schema 6 adds optional gradient-stop `opacity` in [0,1], defaulting to 1 for existing artwork. Nonfinite/out-of-range values are rejected. Older readers reject schema 6 rather than silently dropping stop transparency. Schema-5 directories upgrade without rewriting asset bytes. Stops retain six-digit RGB colors independently of opacity.

Schema 7 adds optional gradient `transform: [a,b,c,d]`, a nonsingular local paint basis pivoted about `from`. Missing basis means identity. Entries must be finite and bounded by 100, with absolute determinant at least 1e-6. The basis transforms the gradient independently of shape geometry and supports elliptical radial fills and skew. Text gradients also accept the basis; Canvas/export rendering masks glyphs independently of paint transforms. Schema-6 directories migrate without changing asset bytes; older readers reject schema 7.

Schema 8 adds optional brush `response`, a finite pressure-to-width exponent in [0.25,4], defaulting to 1. Raw pressure samples stay unchanged; response applies after interpolation. Older readers reject schema 8 instead of silently dropping the curve. Schema-7 directories migrate while preserving IDs and asset bytes. Future versions remain rejected.

Schema 9 adds optional boolean brush `twist`, default false. It enables saved point twist to contribute to nib rotation, interpolated by shortest arc. Non-boolean values are rejected. Schema-8 directories upgrade without changing IDs or assets; old artwork retains its previous orientation. Older readers reject schema 9 rather than silently ignore rotation.

## Schema 10 bitmap library assets

Schema 10 adds optional asset `bitmap` metadata: name (1–200 characters), integer width/height (1–4096, at most 16 million pixels), and an in-memory PNG data URL. Schema 0–9 projects migrate without changing existing asset IDs or bytes. Asset IDs and paths must be unique. Bitmap paths use `assets/bitmaps/<id>.json`.

Save writes immutable JSON `{dataUrl}` payloads before committing the manifest and omits data URLs from manifest metadata. Existing payloads must match exactly; conflicts fail without replacing files or committing a new manifest. Open hydrates payloads and validates PNG header dimensions. Missing files remain explicit missing references with metadata intact. Removing an asset from the library does not delete its file, preserving old revisions and undo/recovery. Bitmap garbage collection is not implemented.

The input library accepts PNG, JPEG and static WebP through browser decoding and normalizes to PNG. Limits: 4 MB source, 2.8 million encoded data-URL characters per asset, 8 million across the in-memory project. Header dimensions are checked before decode and actual dimensions afterward. Animated WebP is rejected; other multi-frame PNG input is represented by the browser-decoded first frame. Native codecs/platform behavior remain unverified. Browser recovery can exceed localStorage quota and reports the existing save-to-folder warning; the immutable folder save remains authoritative. Schema 11 adds bitmap placement, vector fills and HTML playback as described below.

## Schema 11 bitmap vector paint

Vectors may store `bitmap: {assetId,x,y,width,height,repeat?}` instead of a gradient. It maps one image tile to a positive local rectangle; repeat defaults false. Normalization translates the paint origin along with the local geometry, numeric resize scales the paint rectangle, and object affine transforms carry geometry and paint together. Text bitmap fills and independent rotated/skewed bitmap bases are not yet supported. IDs must reference bitmap metadata in the project; missing on-disk pixel payloads retain that reference but export rejects them. Referenced unique bitmap dimensions are capped at 32 million total pixels. Schemas 0–10 migrate; existing bitmap payload files remain unchanged.

Canvas authoring/export use image patterns clipped by the vector contour; Pixi preview uploads clipped Canvas tiles up to 1024 pixels per side. HTML embeds only referenced PNG assets and waits for decoding before starting its frame clock. Unavailable image pixels show a magenta placeholder in the editor; exports reject missing payloads or display a decode error. Referenced assets cannot be removed through the library. Cross-document vector paste requires its asset already in the destination; automatic asset transfer remains pending.

Schema 12 adds an optional bitmap paint `transform: [a,b,c,d]` basis. Local paint coordinates are origin plus basis times the width/height-scaled source pixel coordinates. Each basis entry is finite and bounded to ±100; determinant magnitude must be at least 0.000001. Reflections are allowed. Schemas 0–11 migrate with identity bitmap bases. Nonuniform numeric geometry resizing conjugates the basis while scaling origin/dimensions, preserving the complete paint map. Existing asset payloads remain immutable.

Schema 13 allows bitmap paint on text. It uses the same shape-local bitmap map as vectors, independently of text glyph scale, wrapping and spacing. Schemas 0–12 migrate without changing artwork or asset bytes. Older readers reject this schema rather than misreading newly supported text paint. Payload/reference/basis limits remain unchanged.

Schema 14 adds optional text `direction` (`ltr`/`rtl`, default `ltr`), `kerning` (`auto`/`normal`/`none`, default `auto`) and `wordSpacing` (finite -20–200 local pixels, default 0). Schemas 0–13 migrate without modifying existing content. Glyph measurement, wrapping and render masks use these fields consistently. Older readers reject the schema. Fonts and script shaping remain supplied by the host browser/font engine.

Schema 15 adds optional text `runs`: up to 256 disjoint grapheme-aligned UTF-16 ranges with optional bold/italic/font/size/color overrides. Empty overrides inherit the base text style; explicit false remains an override. Ranges and style values use the rich-text validator, and old schemas 0–14 migrate without changing content. Schema 16 permits gradient/bitmap fills with runs; ranges without explicit color inherit that paint, and explicit range colors remain solid. Schemas 0–15 migrate to 16 without rewriting paint or style runs. Schema 15 preserves style runs in immutable project revisions.

Schema 16 integrates gradient and bitmap fills with mixed-style text. Inherited glyphs use an independently transformed paint mask; explicit range colors remain solid. Layout is reused across paint tiles. Canvas/export and WebGL fixtures cover mixed sizes, bidi/wrapping, rotation, opacity, strokes and tile boundaries. Pixi tile bounds are rounded after stroke padding to preserve pixel alignment. Cross-style Arabic/Indic shaping, broad font/native qualification and the full M2 gate remain open.

Schema 17 extends text runs with optional `letterSpacing` (−100–100), `wordSpacing` (−1000–1000) and `kerning` (auto/normal/none). Numbers must be finite. Explicit zero overrides the base; absent fields inherit. Schemas 0–16 migrate without altering content or existing paint/style data.

Schema 18 adds optional project `folders` (up to 128 `{id,name,parentId?}` entries) and layer `folderId`. Names are 1–80 characters, IDs are unique/nonempty, parents and memberships must resolve, cycles are rejected and maximum ancestry depth is eight. Folders are organizational metadata; layer-array order remains paint order. Schemas 0–17 migrate without changing artwork. Collapse state is not persisted.
